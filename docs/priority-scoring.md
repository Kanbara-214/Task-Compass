# 優先度推薦ロジック設計

Task Compass では、従来の「タスク単体に優先度スコアを付けて並べる」方式から、
ユーザーが選択した作業可能時間の中で「今日どのタスクを、どの順番で完了させるべきか」を提示する方式へ見直す。

この文書では、issue #10「優先度計算ロジックの改修」で実装する推薦ロジックの仕様を定義する。

## 解決したい課題

現在の優先度スコアは、重要度、緊急度、締切、作業時間、ステータスを加点して算出している。
この方式には以下の課題がある。

- 期限切れタスクが強く加点され、常に上位に残りやすい
- スコアが高い順に並べても、限られた時間で今日やるべき組み合わせにならない場合がある
- 「今日やるべきタスク」は分かっても、実行順序までは決められない
- Java 側と SQL 側に計算ロジックが分散している

新しい方式では、単体スコアの最大化ではなく、作業可能時間内で得られる報酬の最大化として推薦を考える。

## 入力

推薦ロジックは、以下を入力として受け取る。

- 未完了タスク一覧
- 現在時刻
- ユーザーが選択した作業可能時間

作業可能時間は 15 分刻みで選択する。
初期値は 60 分とする。

選択肢は、まず以下の範囲で用意する。

- 15 分
- 30 分
- 45 分
- 60 分
- 75 分
- 90 分
- 105 分
- 120 分
- 150 分
- 180 分
- 240 分

## 制約

- 選択したタスクの作業時間の総和は、ユーザーが選択した作業可能時間以下とする
- ユーザーは複数タスクを並列で作業することはできない

## 出力

作業可能時間内で完了すべきタスク列を出力する。
タスク列の順序は、推薦ロジックが「次に処理するタスク」を順に選択した結果とする。

## 報酬

推薦ロジックでは、作業可能時間内でタスクを順に選択・処理した結果を以下の報酬で評価する。

```text
報酬 =
  完了できたタスクの重要度合計
  - 作業終了時点で残る期限切れタスクの重要度合計
```

「完了できたタスクの重要度合計」には、すでに期限切れになっているタスクを今回の作業時間内で完了した場合の重要度も含める。

作業時間は分単位で扱うため、締切も日付だけではなく時刻を含む値として扱う。
推薦ロジックでは、現在時刻に各タスクの見積もり作業時間を積み上げ、タスクごとの完了予定時刻を計算する。
締切を過ぎた後に完了したタスクは報酬に含めない。

### すでに期限切れのタスクの扱い

すでに期限切れのタスクは、作業終了時点で残る場合にマイナス評価する。

一方で、今日完了できる期限切れタスクは、期限切れ状態を解消できるためプラス評価にも含める。
これにより、期限切れタスクを無条件に最優先するのではなく、作業可能時間内で解消する価値が高いものだけを選べるようにする。

### 作業時間内に期限を迎えるタスクの扱い

作業時間内に期限を迎えるタスクは、作業終了時点で未完了になると新たに期限切れになる。
そのため、報酬計算では「今回の作業時間内で残すと期限切れ負債になるタスク」として扱う。

具体的には、締切が現在時刻から作業終了予定時刻までの間にあるタスクがタスク列に含まれなかった場合、残る期限切れタスクの重要度合計に含める。

## 推薦アルゴリズム

推薦ロジックは、貪欲法ではなく、締切付きの重み付きスケジューリング問題として扱う。
各タスクを以下の値を持つジョブに変換し、作業可能時間内で報酬が最大になるタスク列を動的計画法で求める。

- `processingTime`: 見積もり作業時間
- `deadline`: 締切時刻
- `value`: そのタスクを今回の作業時間内で完了する価値

`value` は以下のように計算する。

- すでに期限切れのタスク: `重要度 * 2`
- 作業時間内に期限を迎えるタスク: `重要度 * 2`
- 作業時間後に期限を迎えるタスク: `重要度`

すでに期限切れのタスクは、通常の締切判定では必ず締切を過ぎている。
しかし、今回の作業時間内で完了できれば期限切れ状態を解消できるため、推薦計算上は `現在時刻 + 作業可能時間` を実質的な締切として扱う。

作業時間内に期限を迎えるタスクは、実際の締切時刻までに完了できる場合だけ選択できる。
作業時間後に期限を迎えるタスクは、今回の作業時間内に完了できれば報酬に含める。

アルゴリズムの流れは以下とする。

1. 完了済みタスクを除外する
2. 各タスクを `processingTime`, `deadline`, `value` を持つジョブに変換する
3. ジョブを `deadline` 昇順、`value` 降順、重要度降順、見積もり作業時間昇順、ID 昇順で並べる
4. `dp[i][t]` を「先頭 `i` 件のジョブを見て、合計 `t` 分で完了できる最大 value」として計算する
5. ジョブを選ぶ場合は、`現在時刻 + t + processingTime` がそのジョブの `deadline` 以下である場合だけ遷移する
6. 最大 value の状態から選択されたジョブを復元する
7. 復元したジョブを締切順に並べたものを、推薦タスク列として返す

同じ value になる候補が複数ある場合は、タイブレークを固定して推薦結果を安定させる。
優先順は、締切が早い、重要度が高い、見積もり作業時間が短い、ID が小さい順とする。

## SQL と Java の責務

新しい推薦ロジックでは、優先度計算を Java 側に集約する。

SQL 側の責務は、タスクの並び替えやフィルタリングをしたうえで取得することだけに限定する。

Java 側の責務は、以下とする。

- 残り作業可能時間と未完了タスクの状態を管理する
- 報酬が最大になるタスク列を選択する
- 選択結果としてタスク列を作る
- 最終状態の報酬を計算する
- 推薦理由や表示用の補足情報を作る

## ダッシュボード表示

ダッシュボードの「今日やるべきタスク」は、単なる優先度上位ではなく、選択された作業可能時間内で推薦されたタスク列として表示する。

表示する情報は以下とする。

- 作業可能時間の選択プルダウン
- 推薦されたタスクの実行順序
- 各タスクの見積もり作業時間
- 合計作業時間
- 推薦理由
- 今日の作業時間内では選ばれなかった期限切れタスク数
- 「今週締切のタスク」の削除

## テスト方針

主要ケースとして、以下をテストする。

- 完了済みタスクが推薦対象外になる
- 期限切れタスクが無条件に全て選ばれるわけではない
- 作業時間内に期限を迎えるタスクが適切に選ばれる
- 高重要度の期限切れタスクを解消すると報酬が改善する
- 締切超過後に完了するタスクが報酬に含まれない
- 同じ報酬の候補でタイブレークが安定する

## 今回は扱わないこと

以下は今回の改修では扱わない。

- ユーザーごとの重み調整
- カテゴリごとの優先度補正
- 実績作業時間を使った見積もり補正
- 複数タスクの並列作業
- 機械学習による推薦
