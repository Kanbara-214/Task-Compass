# タスク推薦ロジック設計

Task Compass では、従来の「タスク単体に優先度スコアを付けて並べる」方式から、
ユーザーが選択した作業可能時間の中で「今日どのタスクを、どの順番で完了させるべきか」を提示する方式へ見直した。

この文書では、PR #12 で実装した推薦ロジックの仕様を定義する。

## 解決した課題

従来の優先度スコアは、重要度、締切、作業時間、ステータスなどを加点して算出していた。
この方式には以下の課題がある。

- 期限切れタスクが強く加点され、常に上位に残りやすい
- スコアが高い順に並べても、限られた時間で今日やるべき組み合わせにならない場合がある
- 「今日やるべきタスク」は分かっても、実行順序までは決められない
- Java 側と SQL 側に計算ロジックが分散している

新しい方式では、単体スコアの最大化ではなく、作業可能時間内で得られる報酬の最大化として推薦を考える。

## 入力

推薦ロジックは、以下を入力として受け取る。

- 未完了タスク一覧
- 現在時刻
- ユーザーが選択した作業可能時間

現在時刻は、推薦リクエストを受けた時刻とする。
この時刻を作業開始時刻として扱い、以降の完了予定時刻や期限切れ判定を行う。

作業可能時間は 15 分刻みで選択する。
初期値は 60 分とする。

作業可能時間として受け付ける値は、15 分以上 720 分以下の 15 分刻みとする。
UI の表示候補は使いやすさに応じて絞ってもよいが、リクエスト値としてはこの範囲を有効値として扱う。

## 制約

- 選択したタスクの作業時間の総和は、ユーザーが選択した作業可能時間以下とする
- ユーザーは複数タスクを並列で作業することはできない
- タスクは 1 件ずつ順番に処理する
- 合計作業時間が作業可能時間と等しい場合は、作業可能時間内に完了できたものとして扱う
- 完了予定時刻が締切時刻と等しい場合は、締切内に完了したものとして扱う
- タスクの予想作業時間は既存バリデーションにより 15 分以上、720 分以下とする
- 推薦ロジックでは、作業可能時間とタスクの予想作業時間を分単位で扱う
- 作業可能時間の選択は 15 分刻みとする
- `IN_PROGRESS` は `TODO` と同じ未完了タスクとして扱い、追加加点はしない

## 出力

作業可能時間内で完了すべきタスク列を出力する。
タスク列の順序は、推薦ロジックが「次に処理するタスク」を順に選択した結果とする。

作業可能時間内に完了できる未完了タスクがない場合、推薦タスク列は空とする。
ダッシュボードでは、選択した作業時間内で完了できるタスクがないことを表示する。

## 報酬

推薦ロジックでは、作業可能時間内でタスクを順に選択・処理した結果を以下の報酬で評価する。

```text
報酬 =
  完了できたタスクの重要度合計
  - 作業終了時点で残る期限切れタスクの重要度合計
```

「完了できたタスクの重要度合計」には、すでに期限切れになっているタスクを今回の作業時間内で完了した場合の重要度も含める。

作業時間は分単位で扱うため、締切も日付だけではなく時刻を含む値として扱う。
推薦ロジックでは、現在時刻に各タスクの見積もり作業時間を積み上げ、タスクごとの完了予定時刻を計算する。
締切を過ぎた後に完了したタスクは報酬に含めない。

この問題は、ユーザーが未完了タスクの中から 1 件を選んで処理する行動を繰り返したときに、最終的な報酬を最大化する問題として扱う。
タスクを処理している間に別の未完了タスクが締切を迎えた場合、そのタスクは作業終了時点で残る期限切れタスクとして負の報酬に含まれる。

### すでに期限切れのタスクの扱い

すでに期限切れのタスクは、作業終了時点で残る場合にマイナス評価する。

一方で、今日完了できる期限切れタスクは、期限切れ状態を解消できるためプラス評価にも含める。
これにより、期限切れタスクを無条件に最優先するのではなく、作業可能時間内で解消する価値が高いものだけを選べるようにする。

すでに期限切れのタスクを作業可能時間内で完了した場合、そのタスクは以下の 2 つの効果を持つ。

- 作業終了時点で残る期限切れタスクから外れる
- 完了できたタスクとして重要度分の正の報酬を得る

そのため、すでに期限切れのタスクは推薦計算上 `重要度 * 2` の value として扱う。
実際の締切時刻はすでに過ぎているため、締切内完了ではなく、期限切れ解消として評価する。

### 作業時間内に期限を迎えるタスクの扱い

作業時間内に期限を迎えるタスクは、作業終了時点で未完了になると新たに期限切れになる。
そのため、報酬計算では「今回の作業時間内で残すと期限切れ負債になるタスク」として扱う。

具体的には、締切が現在時刻から作業終了予定時刻までの間にあるタスクがタスク列に含まれなかった場合、残る期限切れタスクの重要度合計に含める。

作業時間内に期限を迎えるタスクを締切内に完了した場合も、以下の 2 つの効果を持つ。

- 完了できたタスクとして重要度分の正の報酬を得る
- 作業終了時点で期限切れ負債になることを避ける

そのため、作業時間内に期限を迎えるタスクも推薦計算上 `重要度 * 2` の value として扱う。

### 作業時間後に期限を迎えるタスクの扱い

作業時間後に期限を迎えるタスクも、推薦対象から除外しない。

そのタスクを処理している間に、作業時間内に期限を迎えるタスクや期限切れ解消タスクの報酬を失わない場合、締切が遠いタスクであっても推薦対象になり得る。
これは、締切が遠いタスクでも、作業可能時間内の機会損失が小さいなら今処理すべき、という考え方に基づく。

作業時間後に期限を迎えるタスクは、今回の作業時間内に完了できれば重要度分の value を得る。

## 推薦アルゴリズム

推薦ロジックは、貪欲法ではなく、締切付きの重み付きスケジューリング問題として扱う。
各タスクを以下の値を持つジョブに変換し、作業可能時間内で報酬が最大になるタスク列を動的計画法で求める。

- `processingTime`: 見積もり作業時間
- `deadline`: 締切時刻
- `value`: そのタスクを今回の作業時間内で完了する価値

`value` は以下のように計算する。

- すでに期限切れのタスク: `重要度 * 2`
- 作業時間内に期限を迎えるタスク: `重要度 * 2`
- 作業時間後に期限を迎えるタスク: `重要度`

すでに期限切れのタスクは、通常の締切判定では必ず締切を過ぎている。
しかし、今回の作業時間内で完了できれば期限切れ状態を解消できるため、推薦計算上は `現在時刻 + 作業可能時間` を実質的な締切として扱う。

作業時間内に期限を迎えるタスクは、実際の締切時刻までに完了できる場合だけ選択できる。
作業時間後に期限を迎えるタスクは、今回の作業時間内に完了できれば報酬に含める。

初期実装では、ログインユーザーの未完了タスクをすべて推薦候補とする。
作業可能時間は最大 720 分であり、分単位の動的計画法として扱っても通常利用では十分に軽量に計算できる想定とする。

アルゴリズムの流れは以下とする。

1. 完了済みタスクを除外する
2. 各タスクを `processingTime`, `deadline`, `value` を持つジョブに変換する
3. ジョブを `deadline` 昇順、`value` 降順、`重要度`降順、`見積もり作業時間`昇順、`ID`昇順で並べる
4. `dp[i][t]` を「先頭 `i` 件のジョブを見て、合計 `t` 分で完了できる最大 value」として計算する
5. ジョブを選ぶ場合は、`t` をそのジョブを完了した時点の合計作業時間として扱い、`現在時刻 + t` がそのジョブの `deadline` 以下である場合だけ遷移する
6. 最大 value の状態から選択されたジョブを復元する
7. 復元したジョブは、DPで処理した順序を保ったまま推薦タスク列として返す

同じ value になる候補が複数ある場合は、タイブレークを固定して推薦結果を安定させる。
優先順は、締切が早い、重要度が高い、見積もり作業時間が短い、ID が小さい順とする。

## SQL と Java の責務

新しい推薦ロジックでは、優先度計算を Java 側に集約する。

SQL 側の責務は、タスクの並び替えやフィルタリングをしたうえで取得することだけに限定する。

Java 側の責務は、以下とする。

- 残り作業可能時間と未完了タスクの状態を管理する
- 報酬が最大になるタスク列を選択する
- 選択結果としてタスク列を作る
- 最終状態の報酬を計算する
- 推薦理由や表示用の補足情報を作る

## ダッシュボード表示

ダッシュボードの「今日やるべきタスク」は、単なる優先度上位ではなく、選択された作業可能時間内で推薦されたタスク列として表示する。

表示する情報は以下とする。

- 作業可能時間の選択プルダウン
- 推薦されたタスクの実行順序
- 各タスクの見積もり作業時間
- 合計作業時間
- 推薦理由
- 推薦結果の要約
- 今日の作業時間内では選ばれなかった期限切れタスク数
- 「今週締切のタスク」の削除

「今日の作業時間内では選ばれなかった期限切れタスク数」は、推薦リクエスト時点ですでに期限切れであり、かつ推薦タスク列に含まれない未完了タスク数とする。
作業中に新たに期限切れになるタスクは、この件数には含めない。

推薦結果の要約では、推薦タスク数、合計作業時間、未選択の期限切れタスク数を短く表示する。

新しい推薦ロジックでは、作業可能時間内の推薦タスク列と未選択の期限切れタスク数を中心に表示するため、従来の「今週締切のタスク」は重複情報として削除する。

### 推薦結果の見せ方

推薦ロジックは報酬最大化を目的とするため、ユーザーの直感とずれる表示になる場合がある。

たとえば、以下のようなケースがある。

- A: 明日締切、重要度 5、30 分
- B: 1 週間後締切、重要度 1、15 分
- C: すでに期限切れ、重要度 1、30 分

ユーザーが選択した作業可能時間は 45 分とする。

この場合、A と C を同時に完了することはできない。
一方で、A を選んだ後の残り 15 分で B は完了できるため、推薦結果は A と B になる可能性がある。

これは数理的には正しいが、ユーザーから見ると「期限切れの C があるのに、なぜ 1 週間後でよい B が推薦されるのか」と感じられる可能性がある。
そのため、B を「C より重要なタスク」として見せるのではなく、「A を優先した後の余り時間で完了できる前倒しタスク」として見せる。

表示上は、推薦理由や補足情報で以下を説明できるようにする。

- A は報酬最大化のために優先されたタスクであること
- B は残り時間で完了できるため追加で推薦されたタスクであること
- 未選択の期限切れタスクがある場合、推薦ロジックが期限切れタスクを無視しているわけではないこと

初期実装では、未選択の期限切れタスクは個別の未選択理由までは表示せず、件数と推薦結果の要約で補足する。
将来的に未選択タスクを個別表示する場合は、単なる件数だけでなく、可能であれば「今回の作業時間では入りきらなかった期限切れタスク」として扱う。
これにより、推薦ロジックが期限切れタスクを無視しているように見えることを避ける。

## テスト方針

主要ケースとして、以下をテストする。

- 完了済みタスクが推薦対象外になる
- `IN_PROGRESS` の追加加点を行わない
- 期限切れタスクが無条件に全て選ばれるわけではない
- 作業時間内に期限を迎えるタスクが適切に選ばれる
- 高重要度の期限切れタスクを解消すると報酬が改善する
- 締切超過後に完了するタスクが報酬に含まれない
- 作業可能時間ちょうどに終わるタスク列を完了可能として扱う
- 締切時刻ちょうどに完了するタスクを締切内完了として扱う
- 作業可能時間内に完了できるタスクがない場合は推薦結果を空にする
- 同じ報酬の候補でタイブレークが安定する
- 期限切れタスクが残っていても、残り時間で完了できる将来締切タスクが推薦される場合に、推薦理由と未選択の期限切れタスク数を表示できる

## 扱わないこと

以下は現在の推薦ロジックでは扱わない。

- ユーザーごとの重み調整
- カテゴリごとの優先度補正
- 実績作業時間を使った見積もり補正
- 複数タスクの並列作業
- 機械学習による推薦
